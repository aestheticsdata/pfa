1The idea in one page

Two approaches that answer two different questions — and fit together without friction.

DDD decides what the model is

Which concepts exist, what rules they guard, where one part of the business ends and another begins. The words of the business become the names in the code.

Hexagonal decides where code lives

The domain sits at the centre and knows nothing about NestJS, Prisma, Redis, Tesseract or the disk. Those plug in from outside, through interfaces the domain owns.

Why PFA needed it

The API was organised the standard NestJS way — a folder per feature, a controller, a service. Clean and tested end to end, but the business rules were not a thing you could point at:

SymptomWhy it hurts
Services threw HTTP exceptionsBusiness code knew it ran behind HTTP.
"A line added later joins the group's receipt" lived in one Prisma transactionNothing stopped another path from breaking it.
Implicit category creation written twiceThe two copies could drift — one already had.
Money as a floatSums rounded after the fact.
Every delete called receiptFiles.release() by handForget it once, a file leaks on disk.
Rules testable only against MySQLSlow feedback, rules hidden in queries.
Pragmatic, not dogmatic. Writes go through aggregates; read-heavy screens stay plain queries. The migration was a strangler — one context per PR, the HTTP contract and the database schema frozen, the e2e suite as the safety net.

2DDD: the building blocks

Two halves. Most people only know the second; the first matters more.

3Hexagonal: ports & adapters

Alistair Cockburn, 2005. Same family as Onion and Clean Architecture: dependencies point inwards.

A port is an abstract class

export abstract class SpendingGroupRepository {
  abstract byId(id, ownerId):
    Promise<SpendingGroup | null>;
  abstract save(group): Promise<void>;
}

TypeScript interfaces vanish at runtime. An abstract class is the port, the type and the Nest injection token at once — and holds no code.

What it buys

  • Testability — the domain runs in a unit test in milliseconds, no DB, no Nest container.
  • Replaceability — Tesseract → a cloud OCR, the disk → S3: one adapter class.
  • Readability — open domain/ and you read the business, not the plumbing.

5Layers & the dependency rule

Inside every context, the same four layers — and imports only ever point inwards.

Enforced twice. A Biome rule rejects forbidden imports in domain/ and application/ as you type. src/contexts/architecture.spec.ts reads every import and checks layers and context borders in pnpm test — so breaking the architecture fails the deploy's fast checks, like a type error.

Conventions

  • One use case per user intention: ls application/ is the feature list.
  • Ports are abstract classes in domain/ports/.
  • Exported types in interfaces/<name>Types.ts.
  • Kebab-case files, Nest style.
  • Path aliases only: @contexts, @shared-kernel, @db, @generated…

7An aggregate: SpendingGroup

Several spendings bought on one receipt, each line in its own category. The group is the only way its lines change together — so it is where the rules live.

static merge(input: GroupMerge): SpendingGroup {
  const [first] = input.candidates;
  if (input.candidates.some((c) => !c.date.equals(first.date))) {
    throw new GroupSpansSeveralDays();                          // invariant 1
  }
  // the first receipt found, in the order sent, is the whole group's   (invariant 4)
  const receipt = input.candidates.find((c) => c.receipt)?.receipt ?? null;
  const lines = input.candidates.map((c) => ({ …c, receipt }));
  const group = new SpendingGroup({ …, lines }, true);
  group.record({
    name: SPENDING_EVENT.spendingsMerged,
    receipts: input.candidates.map((c) => c.receipt),             // what may be orphaned
  });
  return group;
}

Errors are domain errors (GroupSpansSeveralDays extends InvalidInputError); one global filter turns them into the exact 400 the route used to send.

8One request, every layer

POST /api/spendings/groups/merge — three spendings of one day become a group.

Shape validation is an HTTP concern (DTO + class-validator); business validation is the domain's. Three lines of orchestration in the use case, zero business rules.

9Domain events

Commands across contexts became events; questions that need an answer now stayed ports.

Why not a message broker?

One process, one database. A broker would add a moving part for nothing. If a second process ever needs the events, the upgrade is a transactional outbox — events written in the same transaction as the aggregate, relayed afterwards. Same port, new adapter.

What stayed synchronous

"Is this category usable?", "which store is this?", "which product type is this line?" need an answer now. Those are ports with an adapter over the other context — an anti-corruption layer, not an event.

10The read side (CQRS)

Writes go through aggregates. Reads go straight to the rows, shaped for the screen.

The daily projection, as pure functions

export function projectionCandidates(viewed: CalendarMonth): ProjectionCandidate[] {
  return [
    { source: PROJECTION_SOURCE.sameMonthLastYear,    month: viewed.plusYears(-1) },  // N-1
    { source: PROJECTION_SOURCE.sameMonthTwoYearsAgo, month: viewed.plusYears(-2) },  // N-2
    { source: PROJECTION_SOURCE.previousMonth,        month: viewed.plusMonths(-1) }, // M-1
  ];  // none found → no tail at all. Never an average.
}
Knowing when not to apply a pattern is the senior part. Loading a year of Spending aggregates to sum them would be slow and pointless. Lightweight CQRS — aggregates for writes, direct queries for reads — is just honest.

11Testing & fitness tests

The architecture is what makes the fast tests possible — and a test keeps the architecture.

it("refuses to merge spendings from two different days", () => {
  const monday = candidate("a");
  const tuesday = candidate("b", { date: CalendarDay.of("2026-11-17") });
  const merge = () => SpendingGroup.merge({ …, candidates: [monday, tuesday] });
  expect(merge).toThrow(GroupSpansSeveralDays);
});
// no DB, no Nest, no Redis. Before the refactor, only an e2e test against MySQL covered it.

When the fitness test first ran it found a real violation: budget planning's domain types imported Prisma's Decimal. Amounts became decimal text — the same JSON on the wire.

12The migration, ticket by ticket

A strangler fig: the new structure grew around the old one until nothing of the old was left.

Each PR was squash-merged, deployed, and checked in production (health, every route registered) before the next. The e2e suite stayed green throughout and grew three suites along the way: groups, receipts, price comparison.

13Trade-offs — the honest version

Every pattern has a price. Saying it out loud is part of using it well.

CostAnswer
More files and indirection (port, adapter, mapper, use case)Paid where rules live — Spending, Receipt reading. Analytics and Identity stay thin on purpose.
Mappers duplicate shapesThat duplication is the decoupling. Keep mappers dumb and tested by round-trip.
Loading whole aggregates can be heavier than a targeted updateManyGroups are small (a receipt's lines). Bulk operations get a dedicated repository method, as long as no rule is bypassed.
Learning curveThe doc, this guide, and the fitness test as a guard-rail.
"Overkill for a personal-finance app"~9k lines of API, OCR, a bulk-read pipeline, price comparison and bots using it daily: past the size where structure pays.

When not to do DDD

  • CRUD with no rules
  • A prototype that will be thrown away
  • A read-only reporting service

Strategic DDD (contexts, language) is almost always useful.
Tactical DDD (aggregates…) only where rules live.

Decisions taken along the way

DecisionWhy
Ports as abstract classesThe port, the type and the Nest token at once.
No typed IDs (UserId…)Casting at every controller for little gain; ownership is in every port's signature anyway.
Events in-process, no brokerOne process, one DB; the outbox is the documented upgrade path.
ReceiptAttached event droppedThe bulk read's candidates are a query over the rows — already the source of truth.
Thin budget planning & price comparisonRules as value objects and pure functions around repository ports; no aggregate where there is no invariant.

14Interview cheat sheet

The 30-second pitch. "My personal-finance API is NestJS + Prisma + Redis, in production with synthetic users running daily against it. As it grew — receipt OCR, grouped receipts, price comparison — the business rules were spread across services that also did persistence and HTTP. I restructured it with DDD and a hexagonal architecture: six bounded contexts, aggregates that own their invariants, ports and adapters so the domain is pure TypeScript, CQRS-style read models for the stats, domain events between contexts, and fitness tests that keep the dependency rule. The migration was a strangler, context by context, with the e2e suite as the contract."
QuestionShort answer
DDD vs hexagonal vs clean?DDD is modelling (what the domain is); hexagonal / clean / onion are structure (dependencies point inward). Same core idea: dependency inversion.
What is an aggregate, how big?A consistency boundary changed in one transaction through its root. Sized by what must hold immediately; small by default. SpendingGroup owns its lines; Category is outside.
Entity vs value object?Identity vs equality by value. Money, UnitPrice, CatalogName: immutable, self-validating, replace primitives.
Where does validation go?Shape at the edge (DTO); business rules in the domain; DB constraints as the last net.
A repository per table?Per aggregate. SpendingGroupRepository saves the group and its lines.
Transactions across aggregates?Avoid them: one aggregate per transaction, events for the rest, an outbox if delivery must survive a crash.
Why abstract classes for ports in Nest?Interfaces are erased at runtime; an abstract class is type and DI token at once.
Isn't CQRS overkill?Full CQRS with two stores, yes. Aggregates for writes, direct queries for reads: just honest.
How do you keep the architecture?A lint rule and fitness tests on every import, in the deploy's checks.
How did you migrate safely?Strangler, one context per PR, HTTP contract and schema frozen, e2e as the contract, deployed and checked each time.
