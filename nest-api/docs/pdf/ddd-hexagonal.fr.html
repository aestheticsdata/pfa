1L'idée en une page

Deux approches qui répondent à deux questions différentes — et s'emboîtent sans friction.

Le DDD décide ce qu'est le modèle

Quels concepts existent, quelles règles ils protègent, où une partie du métier s'arrête et une autre commence. Les mots du métier deviennent les noms du code.

L'hexagonal décide où vit le code

Le domaine est au centre et ne sait rien de NestJS, Prisma, Redis, Tesseract ou du disque. Ils se branchent de l'extérieur, via des interfaces que le domaine possède.

Pourquoi PFA en avait besoin

L'API suivait l'organisation NestJS standard — un dossier par feature, un contrôleur, un service. Propre et testée de bout en bout, mais les règles métier n'étaient pas quelque chose qu'on pouvait montrer du doigt :

SymptômePourquoi ça fait mal
Les services levaient des exceptions HTTPLe code métier savait qu'il tournait derrière HTTP.
« Une ligne ajoutée rejoint le ticket du groupe » vivait dans une transaction PrismaRien n'empêchait un autre chemin de la casser.
Création implicite de catégorie écrite deux foisLes deux copies pouvaient diverger — l'une l'avait déjà fait.
L'argent en nombre flottantSommes arrondies après coup.
Chaque suppression appelait receiptFiles.release() à la mainUn oubli, et un fichier reste orphelin sur le disque.
Règles testables seulement contre MySQLFeedback lent, règles cachées dans les requêtes.
Pragmatique, pas dogmatique. Les écritures passent par des agrégats ; les écrans de lecture restent de simples requêtes. La migration s'est faite en strangler — un contexte par PR, contrat HTTP et schéma de base gelés, la suite e2e comme filet de sécurité.

3Hexagonal : ports & adaptateurs

Alistair Cockburn, 2005. Même famille que l'Onion et la Clean Architecture : les dépendances pointent vers l'intérieur.

Un port est une classe abstraite

export abstract class SpendingGroupRepository {
  abstract byId(id, ownerId):
    Promise<SpendingGroup | null>;
  abstract save(group): Promise<void>;
}

Les interfaces TypeScript disparaissent à l'exécution. Une classe abstraite est à la fois le port, le type et le jeton d'injection Nest — et ne contient aucun code.

Ce que ça apporte

  • Testabilité — le domaine tourne dans un test unitaire en millisecondes, sans base ni conteneur Nest.
  • Remplaçabilité — Tesseract → un OCR cloud, le disque → S3 : une classe d'adaptateur.
  • Lisibilité — on ouvre domain/ et on lit le métier, pas la plomberie.

5Couches & règle de dépendance

Dans chaque contexte, les quatre mêmes couches — et les imports ne pointent que vers l'intérieur.

Vérifiée deux fois. Une règle Biome refuse les imports interdits dans domain/ et application/ pendant la frappe. src/contexts/architecture.spec.ts lit chaque import et vérifie couches et frontières de contextes dans pnpm test — casser l'architecture fait échouer les vérifications du déploiement, comme une erreur de type.

Conventions

  • Un cas d'usage par intention utilisateur : ls application/ donne la liste des fonctionnalités.
  • Les ports sont des classes abstraites dans domain/ports/.
  • Types exportés dans interfaces/<name>Types.ts.
  • Fichiers en kebab-case, style Nest.
  • Alias de chemins uniquement : @contexts, @shared-kernel, @db, @generated…

Par où commencer la lecture

7Un agrégat : SpendingGroup

Plusieurs dépenses achetées sur un même ticket, chaque ligne dans sa catégorie. Le groupe est le seul moyen de changer ses lignes ensemble — c'est donc là que vivent les règles.

static merge(input: GroupMerge): SpendingGroup {
  const [first] = input.candidates;
  if (input.candidates.some((c) => !c.date.equals(first.date))) {
    throw new GroupSpansSeveralDays();                          // invariant 1
  }
  // le 1er ticket trouvé, dans l'ordre envoyé, devient celui du groupe  (invariant 4)
  const receipt = input.candidates.find((c) => c.receipt)?.receipt ?? null;
  const lines = input.candidates.map((c) => ({ …c, receipt }));
  const group = new SpendingGroup({ …, lines }, true);
  group.record({
    name: SPENDING_EVENT.spendingsMerged,
    receipts: input.candidates.map((c) => c.receipt),             // ce qui peut devenir orphelin
  });
  return group;
}

Les erreurs sont des erreurs de domaine (GroupSpansSeveralDays extends InvalidInputError) ; un filtre global les transforme en exactement le 400 que la route envoyait.

8Une requête, toutes les couches

POST /api/spendings/groups/merge — trois dépenses d'un même jour deviennent un groupe.

La validation de forme relève du HTTP (DTO + class-validator) ; la validation métier, du domaine. Trois lignes d'orchestration dans le cas d'usage, zéro règle métier.

9Événements de domaine

Les commandes entre contextes sont devenues des événements ; les questions qui attendent une réponse immédiate sont restées des ports.

Pourquoi pas un broker ?

Un processus, une base. Un broker ajouterait une pièce mobile pour rien. Si un second processus a un jour besoin des événements, l'évolution est une outbox transactionnelle — les événements écrits dans la même transaction que l'agrégat, relayés ensuite. Même port, nouvel adaptateur.

Ce qui est resté synchrone

« Cette catégorie est-elle utilisable ? », « quel est ce magasin ? », « quel type de produit pour cette ligne ? » attendent une réponse immédiate. Ce sont des ports avec un adaptateur sur l'autre contexte — une couche anti-corruption, pas un événement.

10Le côté lecture (CQRS)

Les écritures passent par les agrégats. Les lectures vont droit aux lignes, taillées pour l'écran.

La projection quotidienne, en fonctions pures

export function projectionCandidates(viewed: CalendarMonth): ProjectionCandidate[] {
  return [
    { source: PROJECTION_SOURCE.sameMonthLastYear,    month: viewed.plusYears(-1) },  // N-1
    { source: PROJECTION_SOURCE.sameMonthTwoYearsAgo, month: viewed.plusYears(-2) },  // N-2
    { source: PROJECTION_SOURCE.previousMonth,        month: viewed.plusMonths(-1) }, // M-1
  ];  // rien trouvé → aucune projection. Jamais de moyenne.
}
Savoir quand ne pas appliquer un pattern, c'est ça le niveau senior. Charger une année d'agrégats Spending pour les sommer serait lent et inutile. Un CQRS léger — agrégats pour l'écriture, requêtes directes pour la lecture — c'est juste honnête.

11Tests & tests d'architecture

L'architecture rend les tests rapides possibles — et un test garde l'architecture.

it("refuses to merge spendings from two different days", () => {
  const monday = candidate("a");
  const tuesday = candidate("b", { date: CalendarDay.of("2026-11-17") });
  const merge = () => SpendingGroup.merge({ …, candidates: [monday, tuesday] });
  expect(merge).toThrow(GroupSpansSeveralDays);
});
// ni base, ni Nest, ni Redis. Avant le refacto, seul un test e2e contre MySQL le couvrait.

À sa première exécution, le test d'architecture a trouvé une vraie violation : les types du domaine budget importaient le Decimal de Prisma. Les montants sont devenus du texte décimal — le même JSON sur le réseau.

12La migration, ticket par ticket

Un figuier étrangleur : la nouvelle structure a poussé autour de l'ancienne jusqu'à ce qu'il n'en reste rien.

Chaque PR a été squash-mergée, déployée et vérifiée en production (santé, chaque route enregistrée) avant la suivante. La suite e2e est restée verte tout du long et a gagné trois suites : groupes, tickets, comparateur.

13Compromis — la version honnête

Chaque pattern a un prix. Le dire à voix haute fait partie de bien l'utiliser.

CoûtRéponse
Plus de fichiers et d'indirection (port, adaptateur, mapper, cas d'usage)Payé là où vivent les règles — Dépenses, Tickets. Statistiques et Identité restent minces exprès.
Les mappers dupliquent des formesCette duplication est le découplage. Des mappers bêtes, testés par aller-retour.
Charger un agrégat entier pèse plus qu'un updateMany cibléLes groupes sont petits (les lignes d'un ticket). Les opérations de masse ont leur méthode de repository, tant qu'aucune règle n'est contournée.
Courbe d'apprentissageLa doc, ce guide, et le test d'architecture comme garde-fou.
« Trop pour une appli de finances perso »~9k lignes d'API, de l'OCR, une lecture en masse, un comparateur et des bots qui l'utilisent chaque jour : au-delà de la taille où la structure paie.

Quand ne pas faire de DDD

  • Du CRUD sans règles
  • Un prototype jetable
  • Un service de reporting en lecture seule

Le DDD stratégique (contextes, langage) est presque toujours utile.
Le DDD tactique (agrégats…) seulement là où vivent des règles.

Décisions prises en route

DécisionPourquoi
Ports en classes abstraitesLe port, le type et le jeton Nest à la fois.
Pas d'ID typés (UserId…)Des casts dans chaque contrôleur pour peu de gain ; le propriétaire est de toute façon dans la signature de chaque port.
Événements en mémoire, sans brokerUn processus, une base ; l'outbox est l'évolution documentée.
Événement ReceiptAttached abandonnéLes candidats de la lecture en masse sont une requête sur les lignes — déjà la source de vérité.
Budget & comparateur mincesRègles en objets-valeurs et fonctions pures autour de ports de repository ; pas d'agrégat sans invariant.

14Antisèche d'entretien

Le pitch en 30 secondes. « Mon API de finances perso est en NestJS + Prisma + Redis, en production, avec des utilisateurs synthétiques qui la sollicitent chaque jour. En grandissant — OCR des tickets, tickets groupés, comparateur de prix — les règles métier se sont dispersées dans des services qui faisaient aussi la persistance et le HTTP. Je l'ai restructurée en DDD avec une architecture hexagonale : six bounded contexts, des agrégats qui portent leurs invariants, des ports et adaptateurs pour un domaine en TypeScript pur, des modèles de lecture façon CQRS pour les stats, des événements de domaine entre contextes, et des tests d'architecture qui gardent la règle de dépendance. La migration s'est faite en strangler, contexte par contexte, avec la suite e2e comme contrat. »
QuestionRéponse courte
DDD vs hexagonal vs clean ?Le DDD, c'est la modélisation (ce qu'est le domaine) ; hexagonal / clean / onion, c'est la structure (dépendances vers l'intérieur). Même idée de fond : l'inversion de dépendance.
Qu'est-ce qu'un agrégat, quelle taille ?Une frontière de cohérence modifiée en une transaction via sa racine. Dimensionné par ce qui doit tenir immédiatement ; petit par défaut. SpendingGroup possède ses lignes ; Category est à l'extérieur.
Entité vs objet-valeur ?Identité vs égalité par valeur. Money, UnitPrice, CatalogName : immuables, auto-validants, remplacent les primitifs.
Où va la validation ?La forme à la périphérie (DTO) ; les règles métier dans le domaine ; les contraintes de base en dernier filet.
Un repository par table ?Par agrégat. SpendingGroupRepository sauve le groupe et ses lignes.
Transactions entre agrégats ?Les éviter : un agrégat par transaction, des événements pour le reste, une outbox si la livraison doit survivre à un crash.
Pourquoi des classes abstraites pour les ports en Nest ?Les interfaces sont effacées à l'exécution ; une classe abstraite est à la fois type et jeton d'injection.
Le CQRS, c'est pas trop ?Un CQRS complet à deux bases, si. Agrégats pour écrire, requêtes directes pour lire : juste honnête.
Comment garder l'architecture ?Une règle de lint et des tests d'architecture sur chaque import, dans les vérifications du déploiement.
Comment migrer sans risque ?Strangler, un contexte par PR, contrat HTTP et schéma gelés, e2e comme contrat, déployé et vérifié à chaque fois.
